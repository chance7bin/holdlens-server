# 基金明细异步刷新任务

## 文档信息

| 字段 | 内容 |
| --- | --- |
| 所属版本 | `v0.0.1` |

| 涉及端 | 跨端 |

## 1. 背景

server 需要持续获得基金公开数据，让用户查看账户资产时能够了解对应基金的公开明细。外部数据处理服务的本地命令和 Markdown 报告不适合作为 server 的长期查询事实源，也无法满足统一持久化、权限、审计和接口查询要求。

server 应作为任务编排方和长期业务事实源，提交需要刷新的基金代码，接收结构化结果，并决定结果是否保存、展示、归档或丢弃。

## 2. 目标

- server 能够在后台发起基金公开数据刷新。
- server 只提供完成刷新所需的最小任务信息。
- server 能够接收和保存可用结果、刷新警告和任务状态。
- 用户能够查询账户资产及其对应的最新可用基金明细。
- 查询链路不再依赖外部数据处理服务的本地 Markdown 报告。

## 3. 范围

### 本次包含

- server 创建并下发基金公开数据刷新任务。
- server 接收、校验并处理结构化刷新结果。
- server 保存可用基金公开数据、数据来源和警告。
- server 提供账户资产与基金明细的组合查询能力。
- 刷新任务和用户查询明确表达数据缺失、部分失败及不可用状态。

### 本次不包含

- 不由 server 直接抓取外部基金行情或公开重仓数据。
- 不通过外部服务本地 Markdown 文件提供业务查询。
- 不新增投资建议、交易建议、风险评分或自动调仓能力。
- 不在本版本解决完整登录、角色、家庭账户或共享账户权限体系。

### 产品影响范围

- 业务模块：估值与收益、持仓汇总、外部数据处理集成。
- 涉及端：server API、后台任务、前端或外部调用方。
- 用户入口：账户资产详情或相关查询入口；刷新任务由后台触发。
- 相关业务流程：后台发起刷新、接收结构化结果、保存可用数据、用户查询资产和基金明细。
- 相关业务对象：基金代码、基金公开详情、刷新任务、数据来源、刷新警告和账户资产。

## 4. 用户角色与主要流程

### 4.1 用户角色

- 普通用户：查看自己的账户资产和相关基金公开明细。
- 系统任务：根据产品规则触发基金公开数据刷新。
- 开发和运维人员：排查任务、外部数据源和结果处理问题。

### 4.2 用户故事

- 作为普通用户，我希望查看账户资产时看到对应基金的最新可用公开明细，以便理解自己的基金持仓。
- 作为系统维护者，我希望基金公开数据由后台刷新，以便用户查询时尽量获得及时信息。
- 作为开发和运维人员，我希望刷新过程保留任务状态和安全警告，以便定位失败原因。

### 4.3 主流程

1. server 根据产品规则发起基金公开数据刷新。
2. server 提交基金代码和必要任务上下文。
3. 外部数据处理服务返回结构化基金公开数据。
4. server 校验结果并决定保存、展示、归档或丢弃。
5. 用户或调用方查询账户资产和匹配的基金公开明细。

### 4.4 异常流程

- 任务无法下发或不满足必要条件时，server 保留可诊断的失败状态。
- 部分基金或字段刷新失败时，server 保存成功部分并明确表达警告。
- 结果无法接收或校验失败时，server 不写入无效数据并保留诊断信息。
- 某个持仓没有可用基金明细时，账户资产主体仍然返回，并明确说明明细不可用。

## 5. 需求明细

### 5.1 后台刷新

- server 应支持根据明确的基金代码集合创建刷新任务。
- 刷新任务不应暴露完整用户持仓组合。
- server 应能够区分任务下发、外部处理和结果接收阶段的失败。

### 5.2 结果处理

- server 应接收能够识别原任务的结构化结果。
- server 应校验结果来源和任务归属，避免重复结果造成重复写入或状态回退。
- server 应保存成功数据、数据来源、警告和安全错误摘要。
- 具体请求、响应、状态、幂等和错误语义由已确认契约及本项目 OpenSpec 维护。

### 5.3 账户资产与基金明细查询

- server 应以账户资产和持仓为主事实源，不得使用基金公开数据覆盖用户持仓事实。
- server 只关联当前用户持仓中匹配的基金公开明细。
- 基金明细不存在、过期或刷新失败时，不得影响账户资产主体返回，并应提供清晰状态。

### 5.4 业务规则

- 基金公开数据作为基金详情参考信息，不反向覆盖用户持仓事实。
- 基金公开数据可以全局复用，用户查询仍必须遵守账户和持仓权限边界。
- 外部数据处理结果是否保存、覆盖、展示、归档或丢弃，由 server 决定。
- 缺失或失败信息必须明确表达，不得伪装为有效数据。

### 5.5 权限与可见性

- 只有授权的系统任务或后台调用方可以发起刷新。
- 用户只能查询自己有权访问的账户资产和关联基金明细。
- 日志、任务和结果不得泄露账户名称、资产金额、完整持仓组合或凭据。

## 6. 非功能要求

- 性能体验：刷新任务在后台处理，用户查询不因外部数据源耗时而长时间阻塞。
- 安全与合规：只传递完成任务所需的最小信息，调用和结果处理具备必要保护。
- 可用性：部分基金刷新失败时尽量保留成功部分和明确警告。
- 可诊断性：任务失败和结果处理失败应提供安全、可定位的摘要。

## 7. 验收标准

- [x] 给定有效基金代码集合，当系统触发刷新时，server 能够发起任务并获得结构化结果。
- [x] 给定部分基金刷新失败，当任务完成时，server 保留成功基金数据和失败警告。
- [x] 给定重复或无效结果，当 server 处理时，不重复写入有效结果，也不破坏已有任务状态。
- [x] 给定用户查询账户资产，当部分持仓存在基金公开明细时，server 返回匹配明细；缺失明细不影响资产主体返回。
- [x] 给定任意刷新任务，server 不发送账户金额、真实账户名称或完整持仓组合。
- [x] 给定查询链路，server 不读取外部数据处理服务的本地基金 Markdown 报告。
- [x] 给定任意查询，基金公开数据不覆盖账户、资产或持仓事实。

## 8. 依赖与风险

- 依赖外部数据处理服务提供稳定的基金公开数据处理能力。
- 依赖双方认可的任务和结果契约。
- 外部公开数据源波动可能造成部分失败或数据延迟。
- 异步处理增加结果交付、幂等和状态一致性的复杂度。
- 结果来源保护不足可能导致未经授权的数据写入。

## 9. 未决问题

- 当前无产品层未决问题；后续技术演进由本项目新的 OpenSpec Change 或 ADR 承接。
