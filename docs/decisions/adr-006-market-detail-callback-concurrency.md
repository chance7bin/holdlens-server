# ADR-006 市场详情回调并发与持久化解耦

## 决策信息

| 字段 | 内容 |
| --- | --- |
| 状态 | 提议 |
| 替代关系 | 细化 ADR-002 的 callback 处理边界；尚未替代其现有决策 |

## 1. 背景

市场详情任务由 Agent 异步采集数据，再通过 HTTP callback 将结构化结果交给 Server。当前 Agent 的 `Semaphore(2)` 只限制外部数据采集，数据采集结束后会先释放信号量，再同步发送 callback，因此它不限制 callback 并发。

Server 当前在 callback 请求线程中完成幂等登记、结果校验、按 slice 开启数据库事务、批量 upsert、任务状态收敛和诊断保存，全部完成后才返回响应。处理期间会占用一个 HTTP 工作线程，并在事务执行期间占用数据库连接。单个 callback 的多个 slice 顺序使用连接，但多个 callback 可以并发争用连接池。

当并发量超过 Server 工作线程、数据库连接池或数据库写入能力时，请求会排队并延长响应时间。Agent 发生读取超时后仍会按相同幂等键重试；幂等机制可以防止重复业务数据和状态推进，但不能消除重复 HTTP 请求、线程占用、连接等待和幂等记录竞争。因此可能形成“写入变慢 → callback 超时 → 重试增加 → 资源竞争加剧”的反馈循环。

将 callback 客户端默认超时从 10 秒调整为 60 秒只能减少正常慢写入造成的误报和重试，不是并发容量方案。

## 2. 待决策事项

本 ADR 暂不选择最终方案。后续需要独立决定市场详情 callback 是否继续同步完成持久化，以及 Agent 和 Server 分别在哪一层实施并发控制、背压和失败恢复。

在作出决定前，现有实现继续保持：Server 同步持久化后响应，Agent 使用稳定幂等键重试；不得把 60 秒超时视为已解决连接池耗尽风险。

## 3. 备选方案

### 方案 A：保留同步持久化并增加有界背压

- Agent 对市场详情 callback 设置独立并发上限，或让现有任务信号量覆盖采集与 callback 的完整生命周期。
- Server 为 callback 入口设置有界执行容量；容量不足时快速返回可重试响应，而不是让请求无限排队。
- 优先采用增量结果、缩小 payload 和减少无效 upsert，降低每次事务的连接占用时间。
- callback 只有在持久化和任务状态收敛完成后才返回成功，保持当前完成语义。

### 方案 B：Server 持久化接收后返回 202，再异步消费

- callback 入口先将完整结果或可恢复的处理引用写入可靠 inbox，并完成幂等接收登记。
- inbox 提交成功后返回 HTTP 202；后台消费者按有界并发执行校验、slice 持久化和任务状态收敛。
- 需要明确 `accepted` 与 `processed` 两阶段状态、消费者重试、毒消息、超时回收、监控和人工补偿。
- 仅把任务提交到进程内线程池而不持久化 payload 不满足可靠接收要求，进程退出时可能丢失已返回 202 的结果。

### 方案 C：按 payload 大小或任务类型混合处理

- 小结果同步完成，大型净值或价格历史结果进入可靠异步消费。
- 可以降低常规请求延迟，但会引入两套完成语义和阈值边界，增加测试、运维和故障判断复杂度。

## 4. 决策所需证据

后续讨论前至少采集以下数据：

- callback 总耗时及校验、连接等待、各 slice SQL、任务收敛的分段耗时；
- callback payload 字节数、净值点数、价格 bar 数和批量 SQL 行数；
- 峰值 callback 并发、Agent 实例数和重试次数；
- Tomcat 活跃线程、Hikari 活跃/等待连接、连接获取超时和数据库锁等待；
- 50、95、99 分位响应时间及超过 Agent timeout 的比例；
- Server 在收到请求后、返回响应前发生进程退出时允许采用的恢复语义。

## 5. 影响

- 正向影响：把 callback 超时参数与系统容量问题分开，避免后续仅通过继续增大超时掩盖资源饱和；为同步背压与可靠异步消费的选择建立统一讨论边界。
- 负向影响：在本 ADR 被采纳并由 OpenSpec 实施前，现有同步 callback 仍可能在高并发下占用工作线程和数据库连接。
- 后续动作：补齐上述观测数据，确定容量目标和失败恢复要求，再将本 ADR 更新为已采纳的单一方案；具体实现、迁移和验收场景另建 OpenSpec change。
