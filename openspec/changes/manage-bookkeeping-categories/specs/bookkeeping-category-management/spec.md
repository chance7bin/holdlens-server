## ADDED Requirements

### Requirement: 提供统一且按用户可配置的记账类别

系统 SHALL 统一保存系统类别与用户自定义类别定义，并 SHALL 按模板默认值和用户配置返回当前用户的启用及未添加类别。

#### Scenario: 查询用户类别设置

- **当** 用户按有效收支类型查询类别设置
- **那么** 系统分别返回按用户顺序排列的已启用类别和未添加类别
- **并且** 每个类别包含稳定代码、名称、类型、图标键、来源、顺序和当前活动账目数量

#### Scenario: 用户尚未修改系统类别

- **当** 系统类别没有该用户的配置记录
- **那么** 查询使用系统类别的默认启用状态和默认顺序
- **并且** 查询过程不新增或修改数据库记录

#### Scenario: 查询记账可选类别

- **当** 用户查询新增、筛选或编辑可使用的类别
- **那么** 系统只返回该用户当前已启用的匹配类型类别

### Requirement: 创建用户自定义类别

系统 SHALL 允许用户为支出或收入创建自定义类别，并 SHALL 校验名称、图标、所有权和创建幂等性。

#### Scenario: 创建有效自定义类别

- **当** 用户提交有效类型、去除首尾空白后 1–4 个可见字符的名称、合法图标键和新请求键
- **那么** 系统生成稳定类别代码并创建已启用类别
- **并且** 新类别排在当前类型已启用类别末尾

#### Scenario: 类别名称重复

- **当** 同一用户在同一收支类型下提交与任一系统或自定义类别相同的名称
- **那么** 系统拒绝创建，无论已有类别当前启用或停用

#### Scenario: 图标不合法

- **当** 用户提交不存在于图标目录的图标键
- **那么** 系统拒绝创建且不写入部分数据

#### Scenario: 重复提交创建请求

- **当** 同一用户重复提交相同创建请求键
- **那么** 系统返回第一次成功创建的类别
- **并且** 不创建重复类别

### Requirement: 启用和停用记账类别

系统 SHALL 允许用户启用或停用自己可管理的类别，并 SHALL 在停用时原子软删除该类别的全部活动账目。

#### Scenario: 停用没有活动账目的类别

- **当** 用户停用自己可管理且当前启用的类别
- **那么** 类别进入未添加列表且不再用于新建或修订账目
- **并且** 返回删除账目数量为零

#### Scenario: 停用存在活动账目的类别

- **当** 用户停用自己可管理且存在活动账目的类别
- **那么** 系统在同一事务内停用类别并将当前用户该类别的全部活动账目标记为已删除
- **并且** 后续明细、统计和账单不再包含这些账目

#### Scenario: 停用事务失败

- **当** 配置更新、账目软删除或剩余顺序更新任一步骤失败
- **那么** 整个操作回滚，类别和账目保持操作前状态

#### Scenario: 重新启用类别

- **当** 用户重新启用未添加类别
- **那么** 类别排在当前类型已启用类别末尾并可用于后续记账
- **并且** 此前随停用软删除的账目不恢复

#### Scenario: 越权操作类别

- **当** 用户尝试启停其他用户的自定义类别或不可见类别
- **那么** 系统拒绝操作且不泄露类别归属关系

### Requirement: 调整用户类别顺序

系统 SHALL 允许用户分别调整支出和收入已启用类别顺序，并 SHALL 拒绝不完整或越权的排序快照。

#### Scenario: 保存完整有效顺序

- **当** 用户提交当前类型全部已启用类别代码且每个代码恰好出现一次
- **那么** 系统按提交顺序保存用户配置并在后续查询中返回相同顺序

#### Scenario: 排序集合无效

- **当** 排序包含重复、遗漏、停用、其他类型、其他用户或不存在的类别
- **那么** 系统拒绝整个排序且不保存部分顺序

### Requirement: 提供分组图标目录

系统 SHALL 提供可用于自定义类别的稳定图标键、分组和顺序，并 SHALL 允许多个类别使用同一图标。

#### Scenario: 查询图标目录

- **当** 客户端查询类别图标目录
- **那么** 系统按约定顺序返回十个分组及全部 68 个合法图标键
- **并且** 不返回或存储 SVG 文件内容

#### Scenario: 重复使用图标

- **当** 用户选择已被其他系统或自定义类别使用的图标
- **那么** 系统仍允许创建类别

### Requirement: 现有记账查询识别用户类别

系统 SHALL 使用用户可见类别定义解析条目和统计中的类别名称及图标，并 SHALL 继续只统计活动账目。

#### Scenario: 查询自定义类别条目

- **当** 用户查询包含活动自定义类别账目的明细
- **那么** 条目返回自定义名称和对应图标键

#### Scenario: 查询自定义类别统计

- **当** 用户查询包含活动自定义类别账目的分类统计
- **那么** 分类排行返回自定义名称、图标键、金额和占比

#### Scenario: 修订使用停用类别

- **当** 用户创建或修订账目时提交当前已停用类别
- **那么** 系统拒绝操作且不保存部分修改

### Requirement: 安全迁移现有固定类别

系统 SHALL 保留现有类别代码和账目关联，并 SHALL NOT 在迁移过程中删除或隐藏已经存在的活动账目。

#### Scenario: 迁移已使用的默认停用类别

- **当** 某用户已有使用默认停用类别的活动账目
- **那么** 迁移为该用户保存启用覆盖配置
- **并且** 原账目继续出现在明细、统计和账单中

#### Scenario: 迁移未使用的默认停用类别

- **当** 用户没有使用某个默认停用类别
- **那么** 该类别按模板默认值出现在未添加列表
